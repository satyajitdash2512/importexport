# HB Trade — database

MySQL 8, InnoDB, `utf8mb4`. Raw SQL through a `mysql2` pool and thin
repositories — no ORM. This directory holds the migrations, the benchmark
harness output, and this runbook.

## Layout

Database-per-tenant: control-plane migrations and per-tenant (business) migrations
are separate directories, applied to separate databases.

```
db/
  migrations/
    control/
      001_control.sql       tenant registry, users, roles, permissions, SoD, refresh tokens
    tenant/                  applied to EACH business database (hb_tenant_<code>)
      001_core.sql          tenancy (legal entities/sites), reference & master data
      002_accounting.sql    GL, books, periods, voucher config, posting rules,
                            voucher + posting_line (partitioned) + account_period_balance rollup
      003_trade.sql         orders → shipments → declarations (partitioned) → duty, landed cost,
                            licences, instruments, entitlements, documents, exceptions, stock ledger
      004_views_procs.sql   convenience views + partition-maintenance & rollup-check procedures
      005_ui_fields.sql     display-only text columns the normalized schema doesn't carry
      006_monthly_2027_partitions.sql   split the FY2027 catch-all partition into months
      007_voucher_names.sql denormalized voucher actor names (users live in the control DB)
  bench/
    benchmark-results.md    generated by `npm run bench`
```

## Commands (run from `apps/api`)

```bash
npm run migrate            # apply pending migrations to control + every tenant DB
npm run migrate:control    # control database only
tsx src/scripts/migrate.ts tenant hb_tenant_hbml   # one tenant database
npm run migrate:status     # show applied / pending / changed, per database
npm run migrate:fresh      # DROP and recreate every database, then apply all
npm run seed               # seed control (tenants + users) then each tenant's business data
npm run db:reset           # migrate:fresh + seed

# generator/benchmark target a tenant DB (default hb_tenant_hbml)
npm run generate 250000 120000 hb_tenant_hbml
BENCH_DB=hb_tenant_hbml npm run bench
```

The migration runner records each file's checksum in `schema_migration`; a file
that changed after being applied is refused (use a new migration, or `--fresh`).
DDL runs as `DB_ADMIN_USER`; if that user can't connect it falls back to the app
user, which is enough when the database already exists.

## Design notes

**Partitioning.** `voucher`, `posting_line`, `declaration`, `declaration_line`,
`declaration_levy` and `stock_ledger` are `RANGE`-partitioned on `period_key`
(`YYYYMM` as an INT). Because MySQL requires the partitioning column in every
unique key, their primary key is `(period_key, id)`. Every period-scoped query
prunes to one monthly partition. `sp_extend_partitions(YYYYMM)` adds a month by
reorganizing the `pmax` catch-all.

**Rollups, not scans.** `account_period_balance` holds one row per account per
book per period; the trial balance reads it and never touches `posting_line`.
It is maintained inside the posting transaction. `sp_check_rollup` reconciles it
against the facts on demand (it reports, it never silently corrects).

**No FK across partitioned tables.** InnoDB does not allow foreign keys on
partitioned tables, so the parent/child links between the partitioned trade
tables are enforced in the repository layer, inside the same transaction. Every
such column is marked `-- NO FK: partitioned` in the DDL.

**Money & rates.** `DECIMAL(20,4)` for money, `DECIMAL(18,8)` for rates,
`DECIMAL(20,6)` for quantities — never FLOAT. `mysql2` returns DECIMAL as a
string; repositories coerce at the boundary.

**Gapless numbering.** Statutory voucher numbers are allocated at *posting* under
`SELECT … FOR UPDATE` on `number_series`, never at creation, so the series never
skips. See `src/repos/posting.ts`.
